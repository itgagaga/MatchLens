# MatchLens 项目 Vibe Coding 开发实施与记录说明

## 一、文档用途

本文档用于指导 `MatchLens 体育赛事数据智能统计与态势分析系统` 的 Vibe Coding 开发过程记录。

本项目不是简单提交一个最终代码结果，也不是只展示与 AI Agent 的完整对话记录，而是需要通过规范化的 Vibe Coding 过程，体现以下内容：

- 先进行需求拆解与架构设计；
- 再使用设计模式约束系统结构；
- 在既定架构内进行增量式功能开发；
- 每次功能迭代后进行测试、调整与重构；
- 留存关键提示词、代码变化、测试结果和重构说明；
- 最终证明项目不是一次性生成，而是经过人工判断、架构约束和持续优化完成。

课程设计指导书明确强调，本课程设计应严格遵循“先架构设计、后 AI 迭代编码”的标准化开发流程，采用对话式、增量式、可重构的开发方式，并留存完整迭代与重构痕迹。因此，本项目需要单独整理 Vibe Coding 迭代日志，用于体现开发过程和个人工程判断能力。

---

## 二、Vibe Coding 不是简单聊天记录

### 2.1 不能只提交完整对话

Vibe Coding 迭代日志不是把所有与 AI Agent 的聊天内容原封不动复制下来。

完整聊天记录通常存在以下问题：

- 内容太长，重点不清楚；
- 很多试探性对话与最终实现无关；
- 无法体现每一轮迭代的目标、结果和判断；
- 不方便老师查看项目如何逐步形成；
- 难以说明设计模式如何约束代码结构。

因此，项目层面需要整理的是“开发迭代记录”，而不是“聊天流水账”。

### 2.2 应该记录什么

每一轮 Vibe Coding 记录应重点包含：

- 本轮开发目标；
- 使用的关键提示词或对话摘要；
- AI Agent 给出的主要建议；
- 本人采纳或调整的内容；
- 代码或架构发生的变化；
- 测试结果；
- 发现的问题；
- 重构或优化措施；
- 下一步计划。

换句话说，Vibe Coding 记录要体现：

> 我如何使用 AI Agent 辅助开发，但最终由我进行架构判断、方案取舍、代码约束和重构优化。

## 三、本项目 Vibe Coding 总体原则

### 3.1 先架构，后编码

本项目不能一开始就要求 AI Agent 一次性生成完整系统代码。

正确流程应为：

```text
需求拆解
↓
模块划分
↓
设计模式选型
↓
系统架构设计
↓
项目骨架搭建
↓
功能增量开发
↓
测试调试
↓
架构重构
↓
功能固化
↓
报告整理
```

### 3.2 先通用模型，后具体赛事

由于选题要求“适配多类体育赛事”，本项目不应直接把核心实体全部设计成篮球专用类。

推荐先设计通用模型：

```text
Match              比赛
Team               队伍
Player             参赛成员
MatchEvent         比赛事件
MatchStatistics    统计结果
SportType          赛事类型
EventType          事件类型
```

再通过策略模式适配不同赛事：

```text
BasketballAnalysisStrategy
FootballAnalysisStrategy
VolleyballAnalysisStrategy
GeneralAnalysisStrategy
```

其中：

- 篮球作为主要完整实现对象；
- 足球、排球作为轻量适配对象；
- 通用赛事策略作为兜底策略。

### 3.3 设计模式必须前置约束

本项目计划使用 4 种设计模式：

| 设计模式 | 使用位置 | 解决问题 |
|---|---|---|
| 状态模式 | 比赛状态管理 | 避免未开始、进行中、暂停、已结束等状态错乱 |
| 责任链模式 | 比赛事件校验 | 避免非法事件、非法比分、非法球员导致统计规则混乱 |
| 策略模式 | 多赛事态势分析 | 支持篮球、足球、排球等不同赛事分析规则切换 |
| 观察者模式 | 事件联动更新 | 比赛事件发生后自动更新比分、统计、预警和复盘数据 |

### 3.4 AI Agent 是项目模块，不是聊天工具

本项目中的 AI Agent 指系统内部封装的业务模块，例如：

```text
DataCollectAgent           赛事数据采集 Agent
SituationAnalysisAgent     态势分析 Agent
ReviewReportAgent          赛后复盘 Agent
```

这些 Agent 可以通过本地规则模板实现，也可以调用外部大模型 API 实现。

无论是否真实调用 API，都必须保证：

- Agent 有独立接口；
- Agent 与业务代码解耦；
- Agent 不直接操作数据库；
- Agent 可替换、可扩展、可复用；
- 后续可从本地规则版替换为远程模型版。

## 四、Vibe Coding 六步开发流程

## 第 1 步：需求拆解与模块划分

### 目标

明确 MatchLens 系统要做什么，先分析需求，不直接生成代码。

### 本阶段要完成的工作

- 确认项目选题；
- 明确系统名称；
- 明确主要业务场景；
- 确定适配赛事；
- 拆分通用业务模块和 AI Agent 模块；
- 预判可能出现的代码混乱问题；
- 初步选择设计模式。

### 本项目建议结论

本项目选择：

```text
系统名称：MatchLens 体育赛事数据智能统计与态势分析系统

主要实现赛事：篮球
轻量适配赛事：足球、排球
核心功能：赛事创建、事件录入、数据统计、态势分析、赛后复盘
核心模式：责任链、策略、状态、观察者
```

## 第 2 步：设计模式前置架构约束

### 目标

在编码前先确定系统架构和设计模式使用方式，防止后续 AI 生成代码时出现堆砌、耦合和状态混乱。

### 本阶段要完成的工作

- 确定系统分层；
- 确定 Java 包结构；
- 确定核心实体类；
- 确定设计模式类结构；
- 确定模块调用规则；
- 确定 AI Agent 接口；
- 确定异常处理和数据校验规则。

### 推荐系统分层

```text
表现层
业务服务层
设计模式核心层
AI Agent 封装层
数据层
```

### 推荐包结构

```text
matchlens
├── entity
├── enums
├── service
├── agent
├── strategy
├── state
├── chain
├── observer
├── repository
└── main
```

### 可使用的提示词

```text
请基于 MatchLens 项目的需求拆解结果，完成前置架构设计。

4. 明确每个包、每个核心接口、每个设计模式的职责；
5. 定义 AI Agent 模块接口；
6. 只输出架构设计和类结构说明，暂时不要生成完整业务代码。
```

## 第 3 步：极简核心骨架搭建

### 目标

只生成项目基础结构，不一次性生成完整功能。

### 本阶段要完成的工作

- 创建通用实体类；
- 创建枚举类；
- 创建 service 接口；
- 创建 AI Agent 接口；
- 创建策略模式接口；
- 创建状态模式接口；
- 创建责任链抽象处理器；
- 创建观察者接口；
- 保证项目可以编译。

### 重点要求

本阶段只做骨架，不追求功能完整。

不应该让 AI Agent 直接生成：

- 完整控制台菜单；
- 完整 Web 接口；
- 完整数据库；
- 所有业务逻辑；
- 所有 AI 调用逻辑。

```text
4. 不写复杂界面；
```

## 第 4 步：业务功能增量迭代

### 目标

在既有架构内逐步实现功能，保证“加功能不破坏核心架构”。

### 建议迭代顺序

```text
1. 比赛创建
2. 球队和球员添加
3. 比赛状态流转
4. 比赛事件录入
5. 责任链校验
6. 观察者通知
7. 数据统计更新
8. 策略模式态势分析
9. AI Agent 赛后复盘
```

### 4.1 迭代状态模式

#### 可使用的提示词

```text
请在不改变 MatchLens 项目整体架构的前提下，实现比赛状态模式。
要求：
1. 支持 NOT_STARTED、RUNNING、PAUSED、FINISHED；
2. 不同状态下允许的操作不同；
3. 未开始不能录入比赛事件；
4. 进行中可以录入比赛事件；
5. 暂停中不能录入得分事件；
6. 已结束不能继续修改核心比赛数据；
7. 不要把所有状态判断写成大量 if-else，要通过状态类封装行为。
```

#### 记录模板

```markdown
### 第 4 次迭代：状态模式实现

**时间**：YYYY-MM-DD  
**本轮目标**：通过状态模式管理比赛状态流转。

**关键提示词**：
> 粘贴本轮核心提示词。

**AI Agent 输出摘要**：
- 新增 MatchState 接口；
- 新增 NotStartedState、RunningState、PausedState、FinishedState；
- 将不同状态下的行为封装进状态类。

**本人判断与取舍**：
- 采纳状态类封装方式；
- 避免在 MatchService 中堆叠大量状态判断；
- 明确已结束状态下只能生成复盘，不能继续录入事件。

**代码变化**：
- 新增 state 包相关类；
- 修改 MatchService 的状态切换逻辑。

**测试结果**：
- 未开始状态录入事件被拒绝；
- 进行中状态录入事件成功；
- 已结束状态继续录入事件被拒绝。

**问题与优化**：
- 初始版本状态切换提示不清晰，后续补充异常说明。

**下一步**：
实现事件录入责任链校验。
```

### 4.2 迭代责任链模式

#### 可使用的提示词

```text
请在现有 MatchLens 架构下，实现比赛事件录入前的责任链校验。
要求：
1. 校验比赛是否存在；
2. 校验当前比赛状态是否允许录入事件；
3. 校验球员是否属于当前比赛队伍；
4. 校验事件类型是否适配当前赛事；
5. 校验得分是否合法；
6. 每个校验规则拆分成独立 Handler；
7. 不要把所有校验逻辑写在一个方法里。
```

#### 记录模板

```markdown
### 第 5 次迭代：责任链模式实现

**关键提示词**：
> 粘贴本轮核心提示词。

**AI Agent 输出摘要**：
- 新增 EventCheckHandler 抽象类；
- 新增 MatchExistsHandler、StateCheckHandler、PlayerCheckHandler、ScoreCheckHandler、EventTypeCheckHandler；
- 形成事件校验链。

**本人判断与取舍**：
- 将状态校验也放入责任链中，使事件录入流程更统一；
- 对篮球得分限制为 1、2、3 分；
- 足球和排球使用更简化的校验规则。

**代码变化**：
- 新增 chain 包；
- 修改 MatchService.addEvent() 方法，使其先经过校验链再更新数据。

**测试结果**：
- 非法球员事件被拒绝；
- 篮球 -1 分事件被拒绝；
- 比赛结束后录入事件被拒绝。

**问题与优化**：
- 初始版本 Handler 顺序不清晰，后续调整为基础校验 → 状态校验 → 球员校验 → 事件类型校验 → 得分校验。

**下一步**：
实现观察者模式，录入事件后自动更新统计和复盘数据。
```

### 推荐 Agent 设计

```text
AiAgent
├── DataCollectAgent
├── SituationAnalysisAgent
└── ReviewReportAgent
```

### 本项目可采用的实现方式

本项目可以先使用本地规则模板模拟 AI Agent 输出。

后续如果需要真实 AI API，只需要新增：

```text
RemoteModelAgent
```

不需要修改核心业务代码。

### 可使用的提示词


## 第 6 步：实时调试与架构重构优化

### 目标

检查 Vibe Coding 过程中是否出现硬编码、重复代码、模块耦合、设计模式失效等问题，并进行重构。

### 重点检查内容

| 检查项 | 说明 |
|---|---|
| 是否硬编码 | 赛事类型、事件类型、状态流转是否写死 |
| 是否重复代码 | 不同策略类或 Agent 中是否出现重复逻辑 |
| 是否高耦合 | service 是否直接依赖具体 Agent 或具体观察者 |
| 是否违反设计模式 | 状态判断是否又回到大量 if-else |
| 是否可扩展 | 新增赛事是否只需新增策略类 |
| 是否可替换 | 本地 Agent 是否可以替换为远程模型 Agent |

### 可使用的提示词

```text
请全局检查 MatchLens 项目代码。

3. 检查 AI Agent 是否与业务模块解耦；
4. 在不改变系统功能的前提下进行重构；
5. 输出重构前后对比说明；
6. 说明重构后如何体现“加功能不改核心代码”。
```

## 七、报告中如何体现自己的工作

在课程设计报告中，不能只写“AI 帮我生成了代码”，而应写：

### 7.1 体现架构判断

示例：

```text
在需求拆解阶段，最初方案倾向于直接以篮球赛事为核心建立 BasketballMatch、BasketballPlayer 等专用类。经过分析，考虑到选题要求支持多赛事适配，最终将核心模型抽象为 Match、Team、Player、MatchEvent 等通用实体，并通过 SportType 与 AnalysisStrategy 实现不同赛事扩展，避免系统被限制为单一篮球项目。
```

### 7.2 体现模式选型

示例：

```text
本项目选择责任链模式处理赛事事件校验，原因是比赛事件录入前需要经过比赛状态、球员归属、事件类型、得分规则等多层校验。如果将所有校验写入一个 service 方法，会导致代码冗长且难以扩展。使用责任链模式后，每类校验规则被拆分为独立 Handler，后续新增赛事规则时只需新增处理器或调整链路顺序。
```

### 7.3 体现迭代重构

示例：

```text
在初始迭代中，态势分析策略选择逻辑直接写在 MatchService 中，导致业务服务层同时承担赛事分析策略选择职责。后续重构时，将策略选择逻辑提取到 StrategyContext 中，使 MatchService 仅负责编排业务流程，AnalysisStrategy 负责具体分析规则，从而提升系统可维护性和可扩展性。
```

### 7.4 体现 AI Agent 封装

示例：

```text
本项目没有将 AI 分析逻辑直接写入业务层，而是设计 AiAgent 统一接口，并实现 SituationAnalysisAgent 与 ReviewReportAgent。当前版本采用本地规则模板模拟 AI 输出，后续可替换为 RemoteModelAgent 调用真实大模型 API。该设计保证了 AI Agent 模块的独立性、可替换性与可复用性。
```

## 九、总结

本项目的 Vibe Coding 过程应重点体现：

- 不是一次性生成完整代码；
- 不是简单调用 AI 接口；
- 不是提交完整聊天记录；
- 而是先进行架构设计，再在设计模式约束下逐步迭代；
- 每一轮迭代都要有目标、有提示词、有代码变化、有测试结果、有优化记录；
- 最终证明系统经过人工架构判断、AI 辅助编码、设计模式约束和持续重构完成。

因此，Vibe Coding 迭代日志是本项目体现“个人工作过程”和“工程判断能力”的重要材料，也是课程设计报告和答辩的重要支撑。
